# WordFinder：需求与技术选型

> 本文保留需求冻结时的选型与验收规划。当前已实现版本和测量结果优先参见 [实现与验证报告](implementation-and-validation.md)；文中“候选”“待实测”等描述不应理解为尚无应用工程。

记录及补充日期：2026-11-06。本文用于保存需求和开发上下文；库版本、API 与发布能力按该日期核验。已纳入 Windows 10、约一万文件、500MB 单文件、多目录分类、索引进程内存限额和索引体积控制等补充要求。搜索语义以最新澄清为准：按行组合多个目标，各目标可以命中同一行的不同单元格；该规则替代先前“所有目标都在同一单元格”的理解。

用户随后表示“其他按你的建议”，因此此前列出的默认搜索、目录、更新索引、后台退出及复制规则均已采纳，具体见各节；软件版本发布与更新检查采用本轮 GitHub Releases 方案。实现参数仍通过原型测试确定，不将已采纳的交互反复列为待确认。

## 1. 项目目标

使用 C# 开发面向 Windows 10 和普通办公室文员的本地 Excel 全文检索桌面软件。需求规模为约 10,000 个文件，最大单文件按约 500MB 设计。用户手动选择多个本机目录，每个目录对应分类标记；程序只读解析并建立持久化本地索引，随后按一个或多个搜索目标查找匹配行，返回文件、工作表、行号、命中单元格及预览。

500MB 指源文件在磁盘上的大致体积，不是解析内存或解压后文本上限；具体格式和文件总容量仍需样本统计。验收需覆盖约一万文件的总体规模及代表性 500MB 大文件。

首次建立索引需要读取实际内容。后续常规搜索只访问本地索引，无需重新打开或解析源 Excel。

## 5. 建议的 C# 技术路线

| 部分 | 建议选型 | 原因及边界 |
| --- | --- | --- |
| 运行时 | .NET 10 LTS 候选 | 以 Windows 10 为目标；结合具体系统版本、架构、支持矩阵和兼容实测锁定运行时 |
| 桌面 UI | WinForms 优先验证，WPF 可选 | 以简单标准控件、启动速度、空闲内存和结果列表响应的实测结果选定 |
| Excel 读取 | ExcelDataReader 逐行 Reader | 用户倾向流式读取；边读边入库，避免积累整本 DataSet |
| 本地存储 | Microsoft.Data.Sqlite | 保存目录标记、文件版本、行列位置和去重文本，按样本验证压缩 |
| 全文搜索 | SQLite FTS5 | 先按目标召回文本/单元格候选，再按文件、工作表、行号组合；减少重复原文和位置记录 |
| 旧格式编码 | System.Text.Encoding.CodePages | 按读取需求注册编码提供者，兼容旧 XLS 编码 |
| 显示格式 | 按需使用 ExcelNumberFormat | 配合格式字符串处理日期、金额和前导零编号 |
| 发布 | .NET 自包含、按架构发布 | 以独立 EXE 为交付目标，包含运行时与原生依赖 |

[.NET 支持策略](https://dotnet.microsoft.com/en-us/platform/support/policy)列明 .NET 10 为 LTS。Microsoft.Data.Sqlite 默认原生依赖包包含 FTS5，见[微软说明](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/custom-versions)。

Windows 10 的不同版本和发行类型需分别验证；运行可用性与厂商支持范围分别记录，不将全部 Windows 10 版本直接视为已验证环境。参考 [.NET 10 支持系统矩阵](https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md)。当前优先建议验证 Windows 10 x64，具体架构尚未由用户确认。

ExcelDataReader 提供值读取和格式字符串获取，显示文本需另行格式化。旧 XLS 编码配置与格式化方法见其 [3.9.0 文档](https://github.com/ExcelDataReader/ExcelDataReader/blob/v3.9.0/README.md)。

### 5.1 WinForms 与 WPF 的选择原则

当前界面以输入框、表格、按钮和进度条为主，先以 WinForms 标准控件作为实现候选。此选择是针对简单办公工具的工程建议，尚没有本项目实测证明 WinForms 一定比 WPF 更省内存。

框架最终取舍应比较相同功能、相同数据页、相同 .NET 版本和 Release 发布方式下的冷启动时间、空闲提交内存、工作集、滚动与查询结果更新延迟。不要将不同样式或不同结果条数的程序直接比较。只有运行开销存在实质差异时，才据此决定切换；简单界面的首屏性能还应控制结果缓存与控件数量。

WinForms 结果表格建议只读、分页，必要时使用虚拟模式按需取值，避免将全部命中绑定进内存。框架功能与虚拟模式资料：[WinForms](https://learn.microsoft.com/en-us/dotnet/desktop/winforms/overview/)、[WPF](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/)、[DataGridView 虚拟模式](https://learn.microsoft.com/en-us/dotnet/desktop/winforms/controls/virtual-mode-in-the-windows-forms-datagridview-control)。

### 5.2 初次索引的内存上限

用户已确认内存额度只限制索引进程，主界面单独计量并展示总体资源情况。默认额度、可选范围和计量口径仍需验证。对普通用户可以提供“省资源 / 均衡”预设与自定义 MiB 输入，预设数值通过包含约 500MB 文件的真实样本确定。

建议采用以下实现边界：

1. 主界面负责搜索和任务管理，独立工作进程负责解析与索引写入；内存不足或解析失败不导致主界面一起退出。
2. 默认单文件解析，队列、待写入批次和数据库缓存设置上限。低资源模式降低后台优先级，提供暂停、继续和取消；CPU 与磁盘竞争也需实测，降低优先级不代表固定的 CPU 百分比限制。
3. 普通文件边读边写，不构造整本 DataSet；共享字符串表等解析器内部结构单独纳入峰值评估。流式接口不能保证任意文件都能在任意小额度内完成。
4. 如需硬限制，使用 Windows Job Object 的提交内存限额约束索引工作进程，同时配置较低的运行预警阈值。提交内存与任务管理器中的物理工作集不同，该额度也不是系统文件缓存的上限。
5. .NET GC 堆限额只覆盖托管堆及 GC 记账，无法独自限制运行时、原生 SQLite 等全部进程开销；可作为辅助配置，不能代替进程级限额。相关 GC 设置通常在进程启动时生效，修改配置后应在下次启动工作进程时应用。
6. 达到预警时先停止新增工作、减小应用缓存；若当前文件在解析器内部仍超出额度，则结束或回收该工作进程，保留已有有效索引，将该文件标记为“内存不足，未完成”。不能仅靠暂停来释放已分配的共享字符串表，也不能无限重试同一文件。
7. 用户可以提高额度后重试，或明确选择跳过该文件；若采用磁盘溢出能力，应验证所用解析器版本、临时目录和磁盘空间。降低内存额度允许牺牲索引速度，不能静默丢失内容或将未完成文件标为已完成。

Windows 限额的定义见 [Job Object 内存结构](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information)；GC 堆限额及启动配置边界见 [.NET GC 配置](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/garbage-collector#heap-hard-limit)。以上是实现建议，尚未进行内存限制原型测试。

## 6. ExcelDataReader 与 calamine 的区别

### 6.1 选型对比

| 维度 | ExcelDataReader | calamine | 对本项目的影响 |
| --- | --- | --- | --- |
| 实现语言 | C# | Rust | C# 项目直接集成 ExcelDataReader 更简单 |
| 接入方式 | NuGet 引用，调用 .NET API | 本体为 Rust crate；C# 接入通常需原生接口封装或独立工作进程通信 | calamine 会引入跨语言构建、数据传递和发布工作 |
| 主要格式 | XLS、XLSX、XLSB | XLS、XLSX、XLSM、XLSB、ODS 等 | 当前需求重点是 Excel；ODS 是 calamine 的额外覆盖 |
| 数据读取接口 | Read()/NextResult() 等逐行 Reader 接口 | 常用 worksheet_range() 返回内存 Range；当前 XLSX API 另有 worksheet_cells_reader() | calamine 应按具体 API 评估，不能概括为只能整表加载 |
| 内存边界 | 应用可边读边入库，但共享字符串表等仍会占内存 | Range 保存矩形区域数据；单元格读取接口可避免构造整块 Range，仍有工作簿等结构开销 | 两者都需要最大真实文件的峰值内存测试 |
| 性能判断 | 需要测解析、格式化及入库全过程 | 同样需要测完整流程，并计入跨语言传输成本 | 不能仅凭 Rust/C# 推断谁更快或给出固定倍数 |
| 开源协议 | MIT | MIT | 均可作为开源依赖候选，随发布包保留对应声明 |
| 源文件访问 | 可通过只读流读取，无需启动 Excel | 只读电子表格解析库，无需启动 Excel | 均符合不启动 Excel 的方向 |

格式、语言与接口资料：[ExcelDataReader](https://github.com/ExcelDataReader/ExcelDataReader/blob/v3.9.0/README.md)、[calamine 项目](https://github.com/tafia/calamine)、[calamine Reader](https://docs.rs/calamine/latest/calamine/trait.Reader.html)。跨语言接入成本是本项目的工程判断。

calamine 的 [Range 文档](https://docs.rs/calamine/latest/calamine/struct.Range.html)说明其保存单元格向量；当前 [Xlsx API](https://docs.rs/calamine/latest/calamine/struct.Xlsx.html#method.worksheet_cells_reader)另有单元格读取接口。按需加载工作表、生成内存 Range、直接读取单元格是不同的使用方式；评估时需固定版本和 API，并分别核实 XLS/XLSB 的行为。

### 6.2 本项目的建议

优先使用 ExcelDataReader 构建原型：保留完整 C# 技术链，使用现成 Reader 接口，实现读取后立即入库。为解析入口保留可替换边界，便于后续使用相同样本对比其他解析器。

只有在实测证明解析阶段是主要瓶颈，且 calamine 的完整接入方案有足够收益时，再考虑引入 Rust。比较需包含解压、解析、文本转换、跨语言通信、索引写入和发布成本。

### 6.3 版本注意事项

截至记录日期，[NuGet 稳定版为 ExcelDataReader 3.9.0](https://www.nuget.org/packages/ExcelDataReader/)。共享字符串表磁盘溢出功能出现在 [4.0.0-beta1 发布说明](https://github.com/ExcelDataReader/ExcelDataReader/releases/tag/v4.0.0-beta1)，不可按 3.9.0 稳定版已有能力设计。

原型先验证稳定版本；若共享字符串表导致内存超预算，再评估支持磁盘溢出的版本，或对超大 XLSX 采用 Open XML SAX 读取并设计磁盘化共享字符串存储。SAX 的官方说明见[微软大表解析文档](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/how-to-parse-and-read-a-large-spreadsheet)。

## 7. 索引内容与已确认的行搜索语义

首版覆盖所有工作表的非空单元格值、隐藏表/行/列以及文件中已保存的公式结果。保留真实行列坐标；按格式需要生成显示文本，保护日期、金额及前导零编号等信息。公式缓存可能过期或缺失，解析器不承担公式重新计算，见[维护者说明](https://github.com/ExcelDataReader/ExcelDataReader/issues/60)。批注、公式表达式、图表文字和图片 OCR 不列为首版必需内容。

XLS、XLSX、XLSB 纳入格式验证；样本中如存在 XLSM，也纳入只读兼容性验证，不执行宏。英文忽略大小写；首版保留目标中的空格、标点和全半角原样，不额外进行自动拆词或字符折叠。规范化规则需固定版本，不能无意丢失编号信息。

### 7.1 多目标匹配

- 一个搜索目标是一个可配置文本条件，按单元格内容包含匹配；每个目标按完整字面文本解释，不自动按空格拆词，英文默认忽略大小写。复杂查询表达式不列为首版必需能力。
- 同一次搜索中的多个目标按“全部满足”组合，匹配范围是同一文件、同一工作表的同一实际行。
- 各目标可以命中该行不同的单元格，不要求所有目标都出现在同一单元格。
- 每个目标需在某个单元格内完整匹配，不能把相邻单元格的片段拼成目标文本。
- 不允许跨行、跨工作表或跨文件凑齐多个目标。
- 结果按行返回，保留每个目标对应的命中列、单元格坐标和文本。同一行去重一次，重复出现在多个目录分类下也不重复展示该行。
- 同一单元格可以同时满足多个目标，此时该行同样算作全部满足；用户已采纳该默认规则。

例：目标 1 为“张三”，目标 2 为“上海”。

| 数据位置 | 内容 | 预期 |
| --- | --- | --- |
| Sheet1!B12 | 张三 | 与 F12 组合，返回第 12 行 |
| Sheet1!F12 | 上海浦东 | 满足第二目标，命中坐标含 B12、F12 |
| Sheet1!B13 / F14 | 张三 / 上海 | 不组合成结果，因为不在同一行 |
| Sheet2!B12 / Sheet3!F12 | 张三 / 上海 | 不组合成结果，因为工作表不同 |

### 7.2 检索实现建议

中文短词需要专门设计：SQLite trigram 全文查询无法直接覆盖少于三个 Unicode 字符的子串，见 [FTS5 官方说明](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)。

原型验证应用生成的单字、连续双字片段。例如“张三丰”生成“张三”“三丰”；片段编码后交给 FTS5，长目标先召回候选，再对原始单元格文本做包含校验。片段在单元格内生成；单个目标的正确性不能只依赖片段同时出现。

每个目标先得到真实命中的单元格/文本，再投影到所属行并取交集。目录分类和当前有效文件版本也参与过滤。分页应发生在组合条件完成之后，不能先截取每个目标的前几十项再求交集而漏掉结果。可优先从候选较少的目标开始，首屏无需统计全部命中总数。

索引体积通过第 8.5 节方案控制，不能为节省空间而截断可检索文本或丢失匹配行。

## 8. 建议的处理流程与存储

```mermaid
flowchart LR
    A[选择多个本机目录及标记] --> B[扫描并比较文件状态]
    B --> C[后台只读解析]
    C --> D[文本规范化与内容分块]
    D --> E[(SQLite 文本与定位索引)]
    F[多个搜索目标及分类筛选] --> H[各目标召回后按行组合]
    E --> H
    H --> G[匹配行及命中单元格预览]
```

### 8.1 数据模型

| 数据 | 建议保存内容 |
| --- | --- |
| 目录分类 | 目录 ID、规范化本机路径、标记名称、文件与目录标记的关联 |
| 文件状态 | 文件路径、大小、UTC 修改时间、有效索引版本和错误状态 |
| 行与工作表 | 文件版本、工作表 ID/名称、实际行号，形成不可跨表组合的行键 |
| 单元格位置 | 所属行、实际列号、文本 ID，以整数引用减少重复元数据 |
| 文本字典/压缩块 | 完整显示文本及其 ID，按完整文本去重；按需压缩，保留原文差异 |
| 倒排索引 | 文本 ID 与检索 token 的对应关系，便于匹配后反查行和列 |
| 应用配置 | 索引目录、内存设置、数据库及分词规则版本、用户设置 |

优先验证“去重文本 + 单元格位置引用”的方案：相同文本在不同文件反复出现时共享文本记录和倒排项，位置仍分别保留。不同大小写、格式或显示文本不因检索规范化而丢失原始差异。去重通过数据库完成，不在内存维护无界全局字典。

重复率低时，该方案的元数据成本可能较高，需与行/内容块存储对照测试后锁定。压缩块大小和位置编码以体积、随机读取速度及内存预算共同决定。行预览由本地保存的文本和位置还原，常规查询不回读源 Excel。

目录由用户手动添加，默认使用末级目录名作为可编辑标记，路径用于区分同名目录；采用递归扫描。重叠目录下的同一文件按规范化路径只解析一次，可关联多个目录标记。重命名标记只改分类元数据，不重读 Excel；移除目录标记不修改源文件，仍属于其他已选目录的文件保留其索引。

### 8.2 首次索引

1. 枚举用户添加的本机目录，维护分类标记，合并重叠路径，按实际格式识别文件并忽略 Excel 临时锁文件。首版不扫描 UNC 共享路径或映射网络盘。
2. 读取文件元信息，将待解析文件放入有界队列。
3. 默认同时解析一个文件，逐行处理、跳过空值并保留实际坐标。
4. 边读取边生成文本和索引词，批量写入数据库，不积累整本 DataSet。
5. 提交成功后记录有效版本和文件状态，显示进度与失败原因。

建议索引任务运行在可退出的独立工作进程中，同一 EXE 可按内部参数启动该进程。任务完成后退出以释放解析期间的内存；用户通过图形界面操作。

工作进程按第 5.2 节执行内存限额。记录已完成文件，程序退出或重启后可从未完成文件续跑；首版建议按文件恢复，正在解析的单个文件允许重新开始，不预设从某个 XML 行或单元格断点继续。

### 8.3 增量更新

1. 根据路径、大小、UTC 修改时间快速识别新增和变化文件；未变化文件跳过解析。
2. 对变化文件写入新的索引版本，旧版本继续可查询。
3. 比较解析前后文件状态，读取期间有变化则重试，避免提交明显不稳定的结果。
4. 新版本构建完成后，通过事务切换当前有效版本，随后清理旧内容和对应倒排数据。
5. 失败或中断保留旧版本，标记待重试；错误提示说明结果可能来自旧索引。
6. 同步清理已删除文件的索引；仅在对应目录成功扫描后判断删除，目录不可访问时不直接清空索引。

首版由用户点击“更新索引”触发上述增量流程，不默认持续监听或定时扫描。FileSystemWatcher 等后台触发机制可在需要时追加，当前不作为完成首版的前置条件。

上述元信息比较是低成本变化检测方式；需要严格检查“内容改变但大小和时间相同”的情况时，可另加内容哈希校验模式。

若后续增加自动索引触发，可使用 FileSystemWatcher 并配合目录核对。它可能产生重复事件，也可能因缓冲区溢出丢失事件，不能独自承担一致性保证，见[微软说明](https://learn.microsoft.com/en-us/dotnet/api/system.io.filesystemwatcher.error)。该扩展不改变首版手动更新的约定。

### 8.4 查询与资源控制

- SQLite 数据库保存在本机可写目录，建议使用 WAL、单写入者和独立查询连接；读写并发边界见 [SQLite WAL 文档](https://www.sqlite.org/wal.html)。
- 使用事务、复用参数化命令批量入库，见[微软批量写入建议](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/bulk-insert)。
- 查询 token 与 SQL 参数统一处理，用户输入按约定的字面搜索语义解析。
- 查询后台执行，输入防抖建议为 150–250ms；新输入取消旧查询或丢弃过期结果。
- 首屏建议先返回 50–100 条，再分页；默认按文件归组，展开查看命中位置。
- 首屏不依赖遍历全部命中计算总数；队列、数据库缓存及索引进程并发均设置上限。

### 8.5 索引体积与空间管理

用户要求索引不能过大，并已选择“先用样本实测，再定额度”。这是一项明确的非功能需求，当前没有已经确认的固定 GB 上限或压缩比例。

优先验证以下优化：

1. 只保存首版可检索的完整单元格文本和必要定位，不复制整本 Excel、图片、样式对象或额外整行字符串；行预览从单元格引用还原。不能只存文本开头作为全文索引的数据源。
2. 相同文本去重；文件路径、工作表名和目录标记通过 ID 引用，避免在每个单元格重复存储。只有确有需要的原始值、显示值和规范化值才分别持久化。
3. FTS 优先验证 `content=''`、`contentless_delete=1` 和 `detail=none`，减少原文副本和词位置；原文、定位及 FTS 的变更需要保持一致。该模式不承担短语位置或内置原文预览，匹配复核与预览由应用完成。具体能力和版本要求见 [SQLite 文档](https://www.sqlite.org/fts5.html#contentless_delete_tables)。
4. 对较长文本或文本数据块验证压缩，短文本仅在压缩有收益时启用；可优先比较 .NET 内置 [BrotliStream](https://learn.microsoft.com/en-us/dotnet/api/system.io.compression.brotlistream)。在受控块大小下按需解压，不以整库解压作为查询前提。
5. 单字和双字索引按实际查询测试，避免同时叠加多套未经验证的全文、前缀和字符索引。去重率、唯一编号数量和文本长度纳入比较；不凭文件个数估算压缩收益。
6. 更新完成后清理旧版本、无引用文本和废弃倒排项，控制 WAL 与临时文件增长。SQLite 删除后文件可能保留空闲页，闲时压缩需结合额外空间和停顿预算，见 [VACUUM 文档](https://www.sqlite.org/lang_vacuum.html)。

空间统计至少区分“稳定持久占用”和“更新/重建峰值占用”：前者包括数据库、内容存储等持久文件；后者还包括 WAL、临时解析文件、新旧版本并存和压缩整理产生的空间。完整重建不能以稳定占用作为唯一剩余空间估计。

样本报告记录源文件总字节、非空单元格数、不同文本数、内容压缩后字节、位置数据与倒排数据的各自大小，以及索引/源文件体积比。XLSX 本身为压缩容器，不能保证本地索引一定比源文件小，也不预先承诺固定百分比。

确定额度后，提供空间用量、清空/重建和整理入口。接近额度或磁盘不足时停止新增索引任务，保留已有有效版本，明确列出未完成文件，提示清理空间、移除分类数据或调整额度；不能通过静默跳过单元格满足空间上限。

## 9. 界面与交付建议

界面面向普通办公室文员，以目录分类筛选、一个或多个搜索目标输入和只读匹配行列表为核心。主界面支持“添加目标”“添加文件夹”“更新索引”“暂停 / 继续”；资源设置集中到设置页。首版支持预览、复制、打开所在文件夹和打开源文件，显示工作表、实际行号和各目标命中坐标。

复制内容提供命中单元格、整行及路径的简单选项；整行采用制表符分隔，便于粘贴到 Excel，复制的多行使用换行分隔。打开源文件由用户主动触发，交给系统默认关联的 Excel、WPS 或其他程序；目标机缺少关联程序时给出提示。索引和搜索仍不启动 Excel，也不依赖 Excel/WPS 安装；首版不承诺打开后自动跳到指定单元格。

建议默认记住多个索引目录及标记，支持 Enter 搜索、复制内容和基本键盘导航，适配办公室常见屏幕缩放。状态直接显示“已完成多少文件、还有多少、失败多少”；异常按用户要求提示原因、继续其他文件、保留失败列表并提供重试入口。首次索引尚未完成时明确提示“当前只搜索已完成的文件”。

用户已采纳默认后台规则：最小化后继续索引；关闭窗口保存已完成文件的进度并退出主程序与索引进程；再次启动时未完成的单个文件可重新解析。首版不默认开机启动，关闭窗口不转入托盘常驻。

发布建议采用 .NET 自包含单文件方式，按目标架构构建，将 SQLite 原生依赖一并纳入交付。用户已接受索引按本机用户保存与清空/重建等管理建议，默认存储位置采用 `%LocalAppData%\WordFinder`；原文索引作为资料副本管理，加密尚未列为首版要求。运行时可能还有原生库解包文件。独立 EXE 是分发目标，索引数据库属于运行后生成的数据。

自包含包包含运行时，体积需实测；WinForms 与 WPF 当前均有常规裁剪限制，不应直接以开启 PublishTrimmed 作为压缩方案。见[单文件发布说明](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview)与[Windows 桌面裁剪限制](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/incompatibilities#windows-platform-incompatibilities)。

用户电脑无需安装 Python、Excel、开发工具或另外的 .NET 运行时。发布验证应覆盖兼容的目标 Windows、普通用户权限、离线环境、原生依赖解包和常用杀毒软件；包体及误报结果以成品测试记录为准。

### 9.1 GitHub 软件版本发布与更新

软件版本通过 GitHub Releases 发布。用户提出 GitHub 更新方向，本轮按轻量交付目标采用“软件内手动检查 + 提示版本及更新说明 + 打开 Release 下载页 + 关闭程序后替换 EXE”的首版流程。Excel 内容的“更新索引”仍是本机操作，与“检查软件更新”使用不同入口。

GitHub Releases 可发布二进制附件，正式下载渠道使用 Release assets。公开资源的版本查询和附件访问无需客户端登录 GitHub；普通用户也无需安装 Git。参考 [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)、[最新 Release API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)及[附件下载 API](https://docs.github.com/en/rest/releases/assets#get-a-release-asset)。

首版实现约定：

1. 发布版本采用统一版本号，正式渠道只提示高于本地版本的稳定 Release，版本比较按数值/版本规则进行。构建结果、版本、架构、变更说明和校验信息一并发布。
2. 用户点击“检查软件更新”后，后台查询配置仓库的最新 Release，显示新旧版本和发布说明，再由用户打开下载页。启动搜索界面不等待网络，不提供静默强制更新，也不常驻轮询。
3. 公共发布方案不在客户端嵌入维护者访问令牌。若源码需保持私有，可使用独立公开发行仓库存放版本说明和程序附件；具体仓库、所有者及代码可见性在发布配置时填写。
4. 设置短超时并处理限流；办公网络无法访问 GitHub 时给出提示，本机索引和检索继续可用。允许用户通过其他可联网电脑下载后拷贝 EXE 升级。GitHub 未认证 REST 请求按来源 IP 计量，多个办公客户端可能共享额度，见[速率限制说明](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)。
5. 更新只替换程序文件，目录标记、配置和索引保存在独立的用户数据目录。新版数据库结构兼容时复用已有索引；结构变化时通过版本检查执行迁移或明确提示重建，纳入磁盘空间与恢复验证。
6. 现阶段不用运行中的主程序自行覆盖 EXE。未来若需要“一键下载、退出、替换并重启”，再验证独立更新器或成熟 .NET 更新组件，保留本地数据兼容与失败恢复能力。

GitHub Actions 可以后续用于构建并上传 Release 附件；临时 workflow artifacts 不作为办公室用户的正式下载入口，其访问和保留规则见[官方说明](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)。本轮只记录方案，尚未配置发布仓库或执行构建/上传。

### 9.2 精简体积与二进制单文件交付

用户要求打包程序尽量裁剪，并以二进制打包运行。当前按“发布已编译、自包含、可双击的单 EXE，尽量减少分发体积”落实，不自动将该表述等同于“必须完全编译为原生机器码”。

| 能力 | 本项目的采用方式 |
| --- | --- |
| 编译后的 EXE | 采用 Release 构建，用户不运行源码或 Python |
| 无需单独安装 .NET | 使用自包含发布，把必需运行时和依赖纳入交付 |
| 单 EXE 分发 | 开启 PublishSingleFile，将原生依赖纳入包；运行时允许按 SDK 机制解包，索引和配置仍在用户数据目录 |
| 尽量缩小体积 | 精简 NuGet 依赖和资源，符号文件单独归档，比较单文件压缩开关；不将减少包体等同于减少运行内存 |
| 自动运行时裁剪 | WinForms/WPF 的常规 SDK 发布不支持直接开启 PublishTrimmed，当前发布基线保持关闭 |
| Native AOT 纯原生编译 | C#/.NET 存在此部署方式，但依赖裁剪且有互操作等限制，不作为当前 WinForms/WPF 完整应用的首版发布基线 |

单文件、自包含及原生库解包的边界见[微软发布说明](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview)。裁剪限制已同时核对[官方兼容性文档](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/incompatibilities)与 [.NET 10 SDK 检查逻辑](https://github.com/dotnet/sdk/blob/v10.0.100/src/Tasks/Microsoft.NET.Build.Tasks/targets/Microsoft.NET.RuntimeIdentifierInference.targets)，不以绕过 SDK 检查作为解决方案。

Native AOT 与普通自包含单文件不同：前者在发布时生成原生代码，后者通常仍携带托管程序集与运行时。Native AOT 的依赖与裁剪边界见[微软说明](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)。如果后续将“纯原生机器码”升级为硬要求，需要重新评估 UI 路线和完整依赖链；当前不为该偏好改变已确定的 C# 开发方向。

首轮发布配置示意如下；现已在应用工程的 Portable 发布配置中实现并完成 x64 打包，具体参数及体积见实现报告，目标电脑兼容性仍需实机验证：

```xml
<PropertyGroup>
  <RuntimeIdentifier>win-x64</RuntimeIdentifier>
  <SelfContained>true</SelfContained>
  <PublishSingleFile>true</PublishSingleFile>
  <IncludeNativeLibrariesForSelfExtract>true</IncludeNativeLibrariesForSelfExtract>
  <EnableCompressionInSingleFile>true</EnableCompressionInSingleFile>
  <PublishTrimmed>false</PublishTrimmed>
  <PublishAot>false</PublishAot>
  <PublishReadyToRun>false</PublishReadyToRun>
</PropertyGroup>
```

其中单文件压缩暂作为对照测试方案：它压缩包内程序集，启动时需要解压到内存，可能增加启动成本。实际发布是否保留该开关，以包体收益、冷/热启动和主界面/索引进程内存实测决定，见[SDK 压缩说明](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview#compress-assemblies-in-single-file-apps)。主界面和独立索引进程均从同一发布包启动，需验证两者的解包与限额行为。

ReadyToRun 基线关闭，以体积为先做对照；它可减少部分启动期 JIT 工作，但也会增加程序集体积，因此不能直接用作“压小包体”的手段，见[官方说明](https://learn.microsoft.com/en-us/dotnet/core/deploying/ready-to-run)。依赖精简只删除明确不用的包和资源，不手工剔除运行时所需 DLL，也不因缩包禁用中文编码、格式化或必要错误信息。

发布时分别记录 EXE 大小、开发侧归档符号、运行解包/缓存和用户数据体积；不提前承诺最终包体为几 MB。GitHub Releases 发布最终 EXE，运行生成的索引不打入程序。

## 10. 验证与验收

先选取约 30–50 个代表性文件，必须包含约 500MB 大文件、主要格式、中文、长编号、前导零、日期、公式、隐藏表和稀疏工作表，并覆盖大量重复值与大量不同编号两类分布。记录机器 CPU、内存、存储介质及文件规模，保证测试可比较。

原型之后再验证约 10,000 个文件下的目录扫描、索引规模、增量更新和查询表现。样本阶段通过不等于已完成一万文件规模验收；源文件总容量和数据分布必须随报告记录。

| 验证项 | 可观察结果 |
| --- | --- |
| 读取完整性 | 用已知匹配样本核对文件、工作表、真实行列坐标与文本 |
| 查询独立性 | 索引成功后，常规查询和预览不依赖源 Excel 可读 |
| 原文件保护 | 在测试中核对源文件内容哈希，索引前后内容不变 |
| 增量效率 | 再次扫描未变化文件时解析次数为零；变化文件被更新 |
| 异常恢复 | 解析失败或工作进程中断，不破坏其他文件和已有有效索引 |
| 检索正确性 | 分别验证中文单字、双字、长词、英文、编号、标点及无匹配输入 |
| 行组合规则 | 同行不同列分别命中多个目标应返回；跨行、跨表、跨文件不能组合；结果保留各目标命中坐标 |
| 多目录分类 | 添加多个本机目录、按标记筛选和重命名标记；重叠路径不重复解析，同一行不因多个标记重复展示 |
| 查询性能 | 记录冷启动/热缓存、索引中/空闲时的首屏延迟和 P95，以及高命中词表现 |
| 资源占用 | 分别记录空闲内存、索引峰值、临时磁盘、索引大小及首次索引总耗时 |
| 索引体积 | 对比去重、压缩、FTS 配置的体积与延迟；分别测稳定占用、增量峰值和完整重建峰值，实测后确定额度 |
| 数据管理 | 验证空间不足时保留有效索引、列出未完成文件，清空/重建不修改源 Excel，删除及整理后的实际占用可观察 |
| UI 开销取舍 | 在同等界面、发布配置和结果条数下记录框架候选的启动、内存、滚动与结果更新指标 |
| 索引内存限制 | 不同额度下验证限额范围、内存不足提示、有效索引保留和提高额度后重试；提交内存与工作集分别记录 |
| 后台办公 | 同时使用典型办公软件时检查响应，验证暂停、继续、最小化运行及重启后按文件续跑 |
| 文员易用性 | 普通用户无需命令行或开发指导，能完成选目录、建立索引、查询、复制路径和失败重试 |
| 文件操作 | 验证预览和复制，用户主动打开文件/文件夹；缺少默认关联程序时给出可理解提示 |
| 独立交付 | 在目标 Windows 10 上，无 Excel、无预装 .NET 运行时仍可双击完成索引和搜索；主动打开文件另验系统关联 |
| 软件版本检查 | GitHub 正式版本提示正确、同版不提示升级；无法联网或限流时不影响本机检索，更新下载入口按架构匹配 |
| 软件替换与数据兼容 | 关闭后替换 EXE 保留目录标记和配置，验证兼容索引复用及结构变化时的迁移/重建提示 |
| 精简单文件发布 | 对照压缩开关记录 EXE 体积、冷/热启动及主界面/索引进程内存，在无预装 .NET 的 Windows 10 上验证原生库解包、中文旧 XLS 编码及全部首版功能 |

普通查询首屏约 200ms 可作为初始优化目标；具体关键词、样本规模、硬件及计时是否包含防抖必须在测试报告中注明。该数值是技术建议，目前没有实测依据；内存、启动时间和包体阈值也需结合样本与目标电脑确定。

## 11. 开发顺序与剩余输入

1. 性能原型：ExcelDataReader 流式读取、索引进程限额、文本去重压缩和中文目标召回，再按行组合；验证约 500MB 文件、索引体积和端到端性能。
2. 最小可用版本：多目录标记、分类筛选、多目标行搜索、持久化索引、预览/复制和打开文件及文件夹。
3. 可靠性完善：版本切换、失败重试、中断恢复、删除同步和目录核对。
4. 发布验证：自包含单 EXE、压缩开关和依赖精简、GitHub Releases 版本检查、升级后数据兼容、普通用户和离线目标机测试，记录包体、启动、运行内存与杀毒软件结果。

上文已将用户确认的系统、规模、行组合语义、范围、目录分类、内存作用范围、异常处理、结果操作和索引管理写入需求，其余默认交互已按用户“其他按你的建议”采纳。核心需求足够开始原型开发，不需要继续逐项确认实现细节。剩余输入用于锁定环境、参数和发布配置。

| 事项 | 剩余信息 | 当前处理 |
| --- | --- | --- |
| 目标电脑细节 | Windows 10 的具体版本/发行类型、架构、物理内存与硬盘类型 | 优先验证 x64；运行时及内存默认值通过目标机和样本确定 |
| 实际数据分布 | 总容量、主要格式、非空单元格量、不同文本比例 | 约一万文件与 500MB 单文件目标已确认，继续补足样本统计 |
| 内存额度 | 默认值、最低值、预设档位和计量细则 | 作用范围已经确认是索引进程，以最大样本测试后定额 |
| 索引额度 | 可接受的稳定与峰值磁盘占用 | 用户已选择样本实测后确定；先落实去重、压缩及精简倒排原型 |
| 程序发布体积 | 单 EXE 压缩收益、解包行为、启动与内存开销 | 按第 9.2 节比较发布配置；尽量精简，不把不受支持的运行时裁剪或 AOT 当作已具备能力 |
| 单字等查询性能 | 高命中词、单字、编号的候选量与响应时间 | 通过样本优化，字面包含、大小写及同行规则已确定，不重复作为待确认问题 |
| GitHub 发布配置 | 仓库所有者、仓库地址和代码可见性，目标电脑是否能访问下载渠道 | 软件内手动检查 Release、下载后关闭替换已记录；地址接入发布流程时填写，不影响解析和搜索原型 |
| 可选后续能力 | 密码输入、结果导出、精确跳单元格、索引加密 | 不阻塞已确认的首版能力；异常按现有失败重试流程处理 |

最新澄清记录：多个搜索目标要求在同一行分别出现，可命中不同单元格；索引体积先用样本实测，再确定额度；其他交互按此前建议采纳，软件更新采用 GitHub Releases 方案；分发尽量精简并采用自包含二进制单 EXE，自动裁剪与 Native AOT 按框架兼容边界处理。未进行真实数据测试前，不承诺固定压缩比例、内存额度或一万文件规模下的查询延迟。

当前已实现 0.1.0：WinForms 界面、ExcelDataReader 逐行解析、SQLite FTS5、独立限额索引进程、同行组合搜索、预览复制、增量恢复和单 EXE 发布。具体库版本、合成规模测试及尚未验证的目标机条件，以 [实现与验证报告](implementation-and-validation.md) 为准。上文关于后续验证的描述保留为验收要求，不代表全部已验收；真实办公样本和 Windows 10 实机验收仍待完成。
